# ตรวจเส้นทางลูกค้าและระบบจองเช่า — 5 ตุลาคม 2026

## ขอบเขตและหลักฐาน

ตรวจโค้ดและการเชื่อมต่อของเว็บไซต์จอง (`index.html`, หน้าราคาเร็ว, รายการเกมและไอดีเกม), LINE Bot และ Delivery App ตั้งแต่เลือกเครื่องถึงคืนค่าประกัน ตรวจหน้าจอมือถือ 375px ภาษาไทยและอังกฤษด้วยเบราว์เซอร์จริงโดยจำลองคำตอบคิว และทดสอบการเลือก Nintendo Switch 1, PS5 และ PS5 Bundle รวมถึงการส่งวันที่จากปฏิทินเข้าแบบจอง ทดสอบชุดเว็บไซต์ 276 รายการ, Bot 546 รายการ, Delivery App 19 ชุดที่เกี่ยวกับราคา คิว การชำระ การสร้าง Booking สัญญา/ตัวตน และการส่งการ์ด พร้อมตรวจ TypeScript ทั้ง Backend และ Frontend ของ Delivery App

ตรวจ API จริงแบบอ่านอย่างเดียว: Bot ส่งนโยบายราคา 17 รุ่นและ Bundle ฿15,000; Delivery App ยังตอบ `policy: null` เพราะยังไม่มีการบันทึกนโยบายผ่าน Admin; ตรวจพบ Delivery App ตอบ 426 ต่อ `/api/public/pricing-policy` ในเบราว์เซอร์และ `/api/integrations/aj-rental/blacklist-check` จาก Bot ก่อนแก้ ไม่มีการใช้ข้อมูลลูกค้าจริง สร้าง Booking จริง ชำระเงินจริง หรือเขียน Google Sheets จริงในการตรวจครั้งนี้ การดึง Gist จากสภาพแวดล้อมตรวจถูก proxy ปฏิเสธ จึงยังยืนยันรายการรุ่นที่เว็บไซต์สดโหลดจาก Gist ไม่ได้

## มุมลูกค้าตามลำดับ

| จุดที่ลูกค้าเจอ | สิ่งที่ระบบทำตอนนี้ | ความเห็นตรงไปตรงมา |
|---|---|---|
| เปิดเว็บ / เห็นเครื่อง | เริ่มที่หน้า “ก่อนเช่า”; กดจองแล้วเลือกเครื่องหรือกดจากการ์ดรุ่นนั้นได้ รายการเกมและไอดีเกมมีทางเข้าของตัวเอง | มีหลายทางเข้า ลูกค้าที่กดจากการ์ดรุ่นใดควรถึงแบบจองของรุ่นนั้นทันที เส้นทางลิงก์รุ่นและวันที่ที่ทดสอบยังคงค่าไว้หลังปิดปฏิทิน |
| เลือกวันและเช็กคิว | เว็บอ่านคิวจาก Bot หรือ Apps Script สำรอง และเช็ก hold ก่อนจอง หากทั้งสองทางอ่านไม่ได้จะขึ้นปุ่มลองใหม่และไม่ให้ข้ามไปชำระ | นี่คือจุดที่ทำให้ลูกค้าหลุดได้มากที่สุดเมื่อ API/เครือข่ายช้า ต้องมีข้อมูลคิวสดก่อนดำเนินต่อ การจำลองคิวผ่านทั้งไทยและอังกฤษแล้ว แต่เบราว์เซอร์ใน workspace ถูก proxy ปิดการเข้าถึง Gist จึงใช้แทนความพร้อมของเครือข่ายลูกค้าจริงไม่ได้ |
| เลือกเกม/Bundle และดูราคา | ยอดเช่า ค่าประกัน ค่าจัดส่ง และส่วนลดคำนวณก่อนสรุป; Bundle คำนวณค่าประกันแทนค่าประกันเครื่อง ไม่บวกซ้ำ | กรอบ “ไม่ยืนยันตัวตน” เดิมแสดงทุกรุ่นจนยาวผิดสัดส่วน ตอนนี้แสดงเฉพาะเครื่องที่เลือกและยอดปกติ → ไม่ยืนยันตัวตน; Bundle แสดงยอดจริงของ Bundle ที่เลือก |
| กรอกข้อมูลและเลือกยืนยันตัวตน | ขอข้อมูลติดต่อ ที่อยู่/หมุด Google Maps และข้อมูลสำหรับคืนค่าประกัน; เลือกไม่ยืนยันได้โดยเห็นยอดค่าประกันที่สูงขึ้น | ลูกค้าต้องกรอกมาก โดยเฉพาะผู้ยืนยันตัวตนภายหลัง การบอกยอดเฉพาะเครื่องตรงจุดตัดสินใจช่วยมากกว่าให้ลูกค้าหาเองในตารางรวม |
| สรุปและชำระ | แสดงยอดและช่องทางชำระ; ลิงก์ชำระต่ออ่านข้อมูลรายการเดิม; webhook เงินเข้า Bot แล้วส่งให้ Delivery App สร้าง/ปรับ Booking | เงินเข้าและ Booking เป็นคนละขั้น หากบริการภายนอกขัดข้องยังต้องมีการ retry/ติดตามจากร้าน ชุดทดสอบครอบคลุมการจ่ายซ้ำ การจ่ายก่อนมี Booking และยอดคงเหลือ แต่ครั้งนี้ไม่ได้ยิงเงินหรือ webhook จริง |
| หลังชำระ/ยืนยันภายหลัง | ระบบส่งการ์ดและอีเมล มีลิงก์ยืนยันภายหลัง; Delivery App ถือการจัดส่งไว้จนคนตรวจเอกสารอนุมัติ | ในมุมลูกค้า “ส่งรูปแล้ว” ยังไม่ใช่ “ส่งเครื่องได้” ควรแจ้งชัดทุกครั้ง ไม่เช่นนั้นลูกค้าจะคิดว่าจ่ายเงินและส่งเอกสารครบแล้วแต่ยังไม่ได้คิวจัดส่ง |
| เตรียมและส่งเครื่อง | ข้อความหน้าเว็บระบุเตรียม 30–60 นาที หรือ 2–3 ชั่วโมงหากต้องลงเกมเพิ่ม แล้วขนส่งอีกประมาณ 1–2 ชั่วโมง | หน้าเว็บมีข้อความ “ส่งด่วน 2 ชม.” ลูกค้าอาจอ่านเป็นเวลารวมตั้งแต่ชำระจนถึงได้รับเครื่อง ทั้งที่งานลงเกมทำให้เกินได้ ควรเขียนเงื่อนไขเวลาประมาณไว้ใกล้คำโฆษณา |
| คืนเครื่อง/คืนค่าประกัน | ร้านเรียกรถกลับ เช็กอุปกรณ์ แล้วคืนตามบัญชีที่บันทึก; Wise รองรับลูกค้าไม่มีบัญชีไทย | ยอดค่าประกันที่แสดงตอนจองต้องตรงกับเงินที่เรียกเก็บและคืน การทดสอบข้ามระบบสำหรับ 4 รุ่นพิเศษผ่าน แต่การคืนเงินจริงยังต้องพึ่งการตรวจ/โอนของร้าน |

## ข้อผิดพลาดที่พบและแก้ในรอบนี้

1. กรอบไม่ยืนยันตัวตนของ Step 2/3 แสดงทุก tier: ลดเหลือ 1 แถวตามเครื่อง/Bundle ที่เลือก ทั้งไทยและอังกฤษ โดยใช้ยอดที่หน้าสรุปคำนวณจริง ส่วน “ขั้นตอนการเช่า” ยังแสดงตารางรวมให้ศึกษา
2. ป้าย Bundle แสดง “อย่างน้อย / at least” และ Nintendo Switch 1 หลุดบรรทัด: ตัดคำนั้นในเว็บและคำอธิบายราคาของ Bot; ครอบชื่อ Nintendo Switch 1 ไม่ให้ตัวเลขหลุดไปบรรทัดใหม่
3. Delivery App บังคับเวอร์ชันแอปกับ public pricing endpoint และ Bot blacklist-check: ยกเว้นเฉพาะสองเส้นทางนี้จาก version gate การตรวจลายเซ็นของ blacklist-check ยังอยู่ที่ route ตามเดิม ก่อนแก้ production ตอบ 426; หลังขึ้นระบบคำขอที่ลายเซ็นผิดตอบ 401 ตามที่ควร
4. ชุดทดสอบเว็บไซต์ 4 รายการไม่ผ่านเพราะยึดรูปแบบโค้ดราคาเก่าหรือคั่นฟังก์ชัน JavaScript ผิด จึงปรับให้ตรวจพฤติกรรมราคาและ tab ปัจจุบัน ตอนนี้ผ่านครบ 276/276

## เรื่องที่ยังต้องเฝ้าดู

- **การซิงก์ราคา:** Delivery App จริงยังไม่มี `Pricing Policy` ที่บันทึกผ่าน Admin (`policy: null`) จึงใช้ fallback เดิม ซึ่งตรงกับราคาเริ่มต้นของ Bot ที่ตรวจได้ในวันนี้ หากร้านเปลี่ยนราคาใน Admin ต้องบันทึกให้การซิงก์สำเร็จและตรวจจำนวน Inventory ที่อัปเดต/เวอร์ชัน Rental Terms ก่อนประกาศราคาใหม่ การตรวจครั้งนี้ไม่ทำการบันทึกแทนร้าน
- **ความครอบคลุมของรุ่น:** fallback ใน HTML เว็บไซต์มี 19 รุ่น ส่วน Bot policy ปัจจุบันมี 17 รุ่น ชื่อ Xbox ต่างตัวพิมพ์แต่ normalize ได้; Viture Luma Pro/Ultra และ XREAL One อยู่เฉพาะ fallback เว็บไซต์ และ Bot มี Viture Pro 2 การเทียบกับ Gist สดทำไม่ได้จาก workspace นี้ จึงยังไม่ยืนยันว่ารุ่นเหล่านี้ถูกเปิดขายบนเว็บจริงหรือไม่ ถ้าเปิดขายควรตรวจราคาและ Inventory ให้ตรงก่อนรับ Booking
- **เวลาส่งเครื่อง:** คำโปรย “ส่งด่วน 2 ชม.” อาจสร้างความคาดหวังเกินกว่าช่วงเวลาลงเกมและรถรับส่งที่ระบุในขั้นตอนเช่า
- **บริการภายนอก:** Google Sheets/Gist, แผนที่, Beam, LINE และ Apps Script เป็นจุดพึ่งพาในทางจอง ไม่มี credentials สำหรับทดสอบด้วยการทำรายการจริงในรอบนี้ จึงสรุปได้ว่าตรรกะและเส้นทางจำลองผ่าน แต่ยืนยันธุรกรรมจริงครบวงจรไม่ได้

## ตรวจหลังเผยแพร่

เว็บไซต์จริงตอบ 200 และมีกรอบค่าประกันตามเครื่องที่เลือก, Bot `/healthz` รายงาน commit `ed905c6`, Delivery public pricing ตอบ 200 แทน 426 และ blacklist-check ตอบ 401 เมื่อส่งลายเซ็นผิด แสดงว่าคำขอไปถึงการตรวจลายเซ็นแล้ว Delivery policy ยังคงเป็น `null` ตามข้อสังเกตด้านบน
